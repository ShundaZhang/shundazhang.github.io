The VM stack

A VM presents a machine interface to a guest operating system. Follow the execution, memory and I/O paths separately.

TermResponsibilityConcrete example
Hypervisor / VMMControls virtual CPU state, address spaces and device access. Implementations divide this work across kernel and userspace.KVM handles virtualization in the Linux kernel. QEMU supplies a machine model and device backends.
Hardware-assisted virtualizationUses CPU virtualization extensions to run compatible guest instructions and intercept selected operations.Intel VMX, AMD SVM, RISC-V H
EmulationSoftware implements the target CPU and machine, allowing an ISA different from the host.QEMU TCG can run a RISC-V guest on an x86 host.
ParavirtualizationThe guest cooperates through a virtualization-aware interface.Virtio drivers and paravirtual clocks can coexist with hardware-assisted CPU execution.
VM managementCreates domains, configures devices and coordinates lifecycle operations.libvirt / virsh / virt-manager

Type 1 commonly describes a hypervisor at the hardware layer. Type 2 describes a VMM hosted by an operating system. For Linux/KVM, inspect the kernel virtualization and userspace device components to understand the actual boundary.

From configuration to guest boot

  • Configure. The manager selects the CPU model, memory, firmware and device backends. A QEMU process allocates guest RAM backing.
  • Create. KVM_CREATE_VM creates a VM handle. The VMM registers memory slots, creates vCPUs and initializes their state.
  • Boot. Firmware or a direct kernel boot path starts the guest OS, which discovers its virtual hardware and loads drivers.

CPU virtualization

A vCPU is saved architectural state plus a schedulable execution context. Ordinary guest computation can stay on the CPU.

ArchitectureExecution controlsMemory / interrupt support
Intel x86 VMXVMX root hosts the VMM, non-root runs the guest. Both have privilege rings. VMCS holds guest/host state and controls, with VMLAUNCH / VMRESUME and VM exits.EPT translates GPA to HPA. APIC virtualization and posted interrupts reduce selected interrupt overhead.
AMD x86 SVMVMCB records guest state and intercept controls. VMRUN enters the guest, with intercepted operations returning control to the VMM.Nested Page Tables (NPT) provide second-stage address translation.
RISC-V H extensionHS-mode manages guests running in VS/VU modes. Virtual supervisor CSRs and trap routing preserve a guest supervisor environment.vsatp controls VS-stage translation, hgatp controls G-stage. Virtual interrupt injection is managed by hypervisor CSRs and applicable interrupt extensions.

A guest syscall normally switches from guest user mode to its own kernel. An exit occurs when an event meets the configured virtualization controls. During a VM switch, registers, interrupt state and relevant control state must remain consistent.

Memory virtualization

The guest owns its process page tables. The hypervisor controls the mapping from guest physical memory to host physical pages.

  • Nested page walks. Guest page-table entries live at GPAs, so reading them also requires second-stage translation. A combined translation cached by the TLB can avoid repeated walks.
  • Two kinds of faults. A guest page fault is handled by its OS for an invalid first-stage mapping. An EPT violation or guest-page fault can transfer control to the hypervisor for a second-stage mapping or permission issue.
  • Shadow paging. The VMM can maintain a composed mapping from GVA to HPA and track guest page-table changes. Hardware-assisted two-stage paging moves the nested translation machinery into the CPU.
  • Mappings need invalidation. Reassigning a host page requires invalidating affected cached translations. Architecture mechanisms include INVEPT / INVVPID and RISC-V HFENCE operations.

In a conventional userspace VMM, a host virtual address (HVA) locates the memory backing a GPA. KVM memory slots associate guest ranges with that backing. HVA belongs to the host process view, while the CPU’s second-stage translation ultimately selects a host physical page.

Devices and DMA

A virtual device needs a programming interface, a data path and a way to notify completion. Device assignment adds DMA isolation requirements.

ModelData pathEngineering trade-off
Emulated deviceGuest driver accesses a model of hardware registers, such as a virtual e1000 NIC.Works with existing device drivers, with register emulation and exit overhead.
VirtioGuest frontend and host backend exchange buffers through shared virtqueues.Requires a compatible guest driver. Batching and notification suppression reduce overhead.
VFIO passthroughThe guest uses an assigned physical device or PCIe function.Needs IOMMU isolation, device reset and suitable host grouping. Device state affects migration support.
SR-IOVA Physical Function (PF) exposes Virtual Functions (VFs), which can be assigned to guests.Guests share physical hardware resources. Firmware, per-VF features and isolation depend on the device.

vhost moves supported Virtio backend processing into the kernel. vhost-user uses a separate userspace backend process, with a control channel to configure shared memory and queues. These optimize where I/O work runs.

Disks and snapshots

The guest sees logical sectors. The host maps them to a file, a block device or a network storage backend.

Raw images map virtual disk offsets with little format metadata. qcow2 adds cluster allocation, reference counts and copy-on-write. A sparse image allocates host storage as data is written. Deleting a guest file releases host space only when discard and the full storage path support reclamation.

Captured stateWhat it gives youConsistency
Disk snapshotDisk contents at a point in timeA running guest may produce crash-consistent state. Guest filesystem freeze and application coordination improve consistency.
Memory + device stateCPU registers, RAM and supported virtual devicesRestore against matching disk state and a compatible virtual machine configuration.
BackupA retained copy with a defined recovery processTest restore, retention and dependency integrity. External services keep their own state.

Durability also depends on guest flush requests, host caching and the storage backend. A snapshot restores local state, while a previously sent network message or committed external transaction keeps its effect.

Virtual networks

Separate the virtual NIC from the virtual switch and the uplink policy. They solve different parts of packet delivery.

ModePacket handlingWhere to inspect

In a cloud, an overlay such as VXLAN can connect tenant networks across hosts using encapsulation. Network identity and policy bind virtual ports to tenants. Place enforcement on the actual packet path, including offloaded or directly assigned devices.

Scheduling and performance

Measure contention, memory locality and I/O queues alongside CPU utilization. Every VM still consumes physical resources.

MechanismPrincipleWhat to observe
vCPU schedulingIn a typical QEMU/KVM setup, vCPUs run in host threads. Several runnable vCPUs may compete for physical CPU time.Guest steal time where supported, host scheduling delay, CPU pinning and SMT contention
NUMA placementKeep guest memory near the CPUs executing it, with a guest topology consistent with host placement.Remote memory access, bandwidth and cross-node placement
Huge pagesLarger mappings can reduce TLB pressure at the guest or host stage, subject to alignment and backing support.TLB misses, fragmentation and available huge-page pools
Ballooning and overcommitA guest balloon driver releases usable guest pages to the host when instructed. Host demand can exceed currently available RAM.Guest memory pressure, swap latency and host OOM risk
KSMRegistered identical pages can share a write-protected host page, copied when written.ksmd CPU work, page sharing and cross-tenant deduplication policy
Queue and thread tuningVirtio multiqueue and I/O threads can distribute work across cores.Queue depth, interrupt rate, p95/p99 latency and backend saturation

Virtual time needs special care when a vCPU is descheduled or moved to another host. KVM clock interfaces and TSC virtualization help guests read a consistent clock. Timer delivery latency can still affect time-sensitive applications.

Migration and nesting

Migration transfers a running machine’s state between hosts. Nesting runs a hypervisor inside a guest.

If dirtying approaches the effective transfer rate, pre-copy may struggle to converge. Post-copy resumes the destination earlier and fetches missing pages on demand, creating a period of dependence on the source. CPU features, device backends and external network identity must be compatible across the move.

Isolation boundaries

Trace which component handles guest-controlled input and which identity can administer the VM.

  • Guest-to-host interfaces. Device descriptors, emulated registers, shared folders, guest agents and management APIs each expose parsing or authorization logic. Limit the enabled devices and backend privileges to the workload.
  • Management and saved state. Protect QMP/libvirt endpoints, VM images, snapshots and migration channels. Stored RAM can contain live credentials and customer data.
  • Shared microarchitecture. Guests can contend for caches, predictors and memory bandwidth. Scheduling, CPU mitigations and tenant placement need to match the chosen isolation requirements.
  • Confidential VMs. TDX and SEV-SNP add protection for private guest state against a privileged host within their threat models. Their attestation and device-sharing rules extend the virtualization design.

For dedicated treatments, continue with TEE, CPU side channels or Agent isolation.

Practice

Use an x86-64 Linux host with QEMU/KVM for these exercises. Keep the virtual machine configuration with your measurements.

Inspect the host and an existing VM

lscpu
ls -l /dev/kvm
qemu-system-x86_64 -accel help
virsh -c qemu:///system list --all
virsh -c qemu:///system dominfo lab-vm
virsh -c qemu:///system dumpxml lab-vm
virsh -c qemu:///system domstats lab-vm

Install QEMU and libvirt using your Linux distribution packages. Replace lab-vm with an existing domain and use an account authorized for that libvirt connection. Record the CPU model, vCPU count, memory backing, NIC model and storage format.

Boot a disposable overlay

Prepare an existing, powered-off x86-64 Linux qcow2 boot image as base.qcow2. Use an image configured for a serial console and an appropriate boot mode. The example uses the default x86 firmware. The commands below create a new overlay in the current directory.

qemu-img info base.qcow2
qemu-img create -f qcow2 -F qcow2 -b base.qcow2 work.qcow2
qemu-system-x86_64 \
  -accel kvm -cpu host -smp 2 -m 2048 \
  -drive file=work.qcow2,format=qcow2,if=virtio \
  -nic user,model=virtio-net-pci \
  -nographic

The overlay references base.qcow2 relative to its own location. It must retain that backing image. This example uses QEMU user-mode networking, which provides a different host-side path from the bridge diagram above. UEFI-only images need a matching firmware configuration. In the default serial multiplexing setup, Ctrl-a x exits QEMU.
